# 0027: Render the Windows companion as a Fluent XAML shell over winio

## Context

The companion draws every control as a winio widget at an absolute position
inside a `TabView` ([ADR 0019](0019-windows-ui-winui3.md)). winio's WinUI
backend places each widget on a `Canvas` and publishes only generic widgets
(`Button`, `CheckBox`, `ComboBox`, `Slider`, `TabView`). Its pinned
`winio-winui3` bindings do not contain `NavigationView`, `ToggleSwitch`,
`NumberBox` or `InfoBar`, and no settings card exists at all. The result cannot
follow the WinUI 3 design language however it is arranged.

A prototype on Windows 11 (Windows App Runtime 1.8) showed that the remaining
gap is small. `XamlReader::Load` is already bound. The window's `Canvas` is
public through `AsContainer::as_container().as_winui()`, so a loaded XAML root
can be appended to it and sized from the window's client size. Bindings for the
missing controls, generated with `windows-bindgen 0.62.1` from the installed
`Microsoft.UI.Xaml.winmd` against `windows-core 0.62`, compile next to
`winio-winui3`. Events from `NavigationView`, `ToggleSwitch` and `NumberBox`
reached winio's `ComponentSender` and the update loop. The prototype's release
executable was 370 KB.

## Decision

winio keeps owning the process: `App`, the event loop, the `Window`, Mica and
the component lifecycle. The visible interface is a Fluent XAML tree hosted in
that window.

1. XAML is constructed only from fixed templates compiled into the companion.
   Strings supplied by plugins are never interpolated into XAML text. They are
   applied after loading through typed property setters (`SetText`,
   `SetContent`, `SetPlaceholderText`), so a plugin cannot inject markup,
   bindings or resource references.
2. Controls are located by `x:Name` and their events are subscribed through
   generated bindings. Handlers only post a winio message; no plugin or IPC work
   runs inside a XAML callback.
3. The bindings are generated by a small Rust tool in `tools/` from an explicit
   list of types, written to a committed source file, and regenerated only when
   that list or the pinned Windows App SDK version changes. The build does not
   read the installed Windows App Runtime. `bindgen`'s `Warnings` result is
   reported, not unwrapped: skipped members whose dependencies were not
   requested are expected.
4. The generated crate is a separate Windows-only library used by the companion.
   Types shared with `winio-winui3` interoperate through COM interface casts,
   not Rust type identity.

## Consequences

The Windows interface is built from real `NavigationView`, cards, `InfoBar`,
`ToggleSwitch` and `NumberBox` controls with system theme, accent colour,
Mica, high-contrast and UI Automation behaviour. `x:Name` becomes the UI
Automation identifier, which the desktop tests use.

The companion carries a generated source file of several hundred kilobytes and
a requirement to regenerate it deliberately when the Windows App SDK pin moves.
Raising that pin requires checking the template markup, because winio hosts the
application resources. The loader, `parsec-orbit-core`, the service plugin and
all other plugins gain no GUI dependency, and the companion's size is measured
separately in the size report.

winio's generic widgets stay available for places that need them. This decision
does not switch the macOS companion, which is addressed by
[ADR 0029](0029-native-design-language.md).
